# 生成任务刷新恢复修复设计

## 目标

修复图片生成任务进行中刷新页面后，任务卡片消失、最终结果无法回到历史记录且没有可见报错的问题。

修复必须保证刷新只会恢复状态查询，不会重新提交付费生成请求。

## 根因

前端在 `runJob` 中持续轮询 `/api/jobs/{jobId}`。页面刷新时，浏览器会中断该轮询请求。当前 `catch/finally` 把页面卸载引起的中断当作任务已经结束处理，随后执行 `clearSavedWork()`，删除 `dialogue-studio-work` 中保存的任务编号。

新页面因此无法得知原任务的 `jobId`，也就无法继续查询后台任务。由于清理发生在旧页面卸载期间，用户看不到错误提示。

## 方案

### 页面生命周期与取消原因

增加页面卸载状态标记，用来区分三种结束原因：

- 页面刷新或关闭：停止旧页面轮询，但保留正在执行和排队任务的本地恢复记录。
- 用户主动停止：按取消任务处理，并清理对应恢复记录。
- 后台任务成功或明确失败：写入历史记录后清理对应恢复记录。

旧页面在卸载期间不得创建“已取消”历史记录，不得显示瞬时错误，也不得清除恢复记录。

### 刷新后的恢复

新页面读取 `dialogue-studio-work` 后，使用原 `jobId` 查询后台状态：

- `running`：恢复进行中任务卡片并继续轮询。
- 返回部分图片：恢复已完成图片和当前进度。
- `completed`：将结果写入历史记录并清理恢复记录。
- `failed`：显示明确失败原因并写入失败记录。
- `404`：提示后台任务状态已丢失；不得自动重新提交生成请求，避免重复扣费。

排队任务继续沿用现有顺序，当前任务完成后再提交下一项。

### 数据边界

浏览器本地记录继续保存任务编号、提示词、模型、尺寸、数量、提交时间和可安全恢复的参考图信息，不保存 API Key。API Key 仍从现有设置项恢复。

后台任务表暂时保持内存实现。本次修复保证普通浏览器刷新可以恢复；如果 Next.js 服务进程真正重启，内存任务状态仍可能丢失，此时必须提示用户，不自动重试付费请求。

## 错误处理

- 页面卸载导致的网络中断不记为生成失败。
- 用户主动停止保持现有取消语义。
- 普通网络错误继续显示，并保留足以重新查询后台任务的状态，除非后台已明确返回最终失败。
- 后台返回任务不存在时，显示“任务状态已丢失，未自动重新生成以避免重复扣费”。

## 测试与验收

1. 创建一个可控的长时间运行任务，刷新页面后任务卡片立即恢复。
2. 在返回部分图片后刷新，已完成图片和剩余数量正确恢复。
3. 连续刷新多次，始终使用同一个 `jobId`，服务端生成接口只提交一次。
4. 任务完成后结果自动进入历史记录，本地恢复记录被清除。
5. 用户主动停止后显示取消状态，不再恢复该任务。
6. 模拟后台任务不存在，页面给出明确提示且不调用创建任务接口。
7. 排队多个任务后刷新，当前任务和队列顺序均能恢复。
8. 运行类型检查和生产构建，并验证历史结果、再次生成及正常新建任务未受影响。

测试不得调用真实付费图片生成。应使用可控的模拟任务或替代响应验证创建次数、轮询恢复和最终状态。

## 不在本次范围内

- 将后台任务状态改为数据库或磁盘持久化。
- 后台服务进程重启后的无损恢复。
- 修改图片生成模型、计费请求或视觉样式。
